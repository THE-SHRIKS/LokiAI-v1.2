# Task Packet — `INC-001 Incident correlation and evidence engine`

Packet status: `accepted` | Graph status: `accepted`
Starting revision: `6d20b5c` (branch `LokiAI-v1.2`, pushed)

## 1. Objective

New crate `crates/loki-incidents`: turns a `MON-002` `RuleEvaluator` `Fired`/
`MissingDataAlert` outcome into a correlated, bounded-evidence incident with
the state machine `Docs/SPEC.md` §4.6 defines exactly, plus assignment,
timeline, verification-window resolution, reopen/close policy, and
work-intent emission per `Docs/SPEC.md` §3's work-intent fields. Read-side/
state-machine engine only — this node does not deliver a work intent to any
provider (that is `AGT-002`, blocked on `AGT-001`/`NOT-001`) and does not
perform any device-changing action itself (that is `OPS-001`/`APR-001`).

## 2. Dependencies and ownership

`depends_on`: `MON-002` (accepted). Writable: new `crates/loki-incidents/**`
+ one `Cargo.toml` members line. Do not touch `crates/loki-monitoring/**`,
`crates/loki-connectors-sdk/**`, or `crates/loki-storage/**` directly — this
node consumes `MON-002`'s `EvaluationOutcome`/`MonitoringRule` types, it does
not modify them.

Note on persistence: this workspace has an established, repeatedly-applied
pattern (see `Docs/graph/handoffs/{MON-001,MON-002}-1.md` §5/§7) for exactly
this situation — a new bounded-context crate that needs its own durable
tables but cannot edit `crates/loki-storage/src/**` (whose migration
registry and connection are both `pub(crate)`-only) is expected to open its
own self-contained SQLite database with its own idempotent migration runner,
not to invent a workaround or silently skip persistence. Follow that same
precedent here rather than re-deriving it from scratch or treating it as a
new stop condition — it is not a new architectural question, it is the third
application of an already-accepted one.

## 4. Deliverables and acceptance criteria

1. Incident model: `incident_id`, title, severity, state, affected scope,
   trigger/rule version, occurrence count, evidence snapshot references,
   assigned user/agent, diagnosis/proposal summaries, verification plan/
   state, timeline, timestamps — matching `Docs/SPEC.md` §3.7's field list
   exactly.
2. State machine matching `Docs/SPEC.md` §4.6's exact diagram: `Open` ->
   `Investigating` -> (`WaitingApproval` | `Verifying` if no device change
   required); `WaitingApproval` -> `Investigating` (denied/expired) or
   `Executing` (approved); `Executing` -> `Verifying` (completes) or
   `Investigating` (fails safely); `Verifying` -> `Resolved` (every check
   passes for the observation window) or `Investigating` (recurrence/failed
   check); `Resolved` -> `Open` (recurrence within reopen policy) or
   `Closed` (retention/policy close). Every edge in the diagram is a real,
   tested transition; no edge not in the diagram is reachable.
3. Correlation: multiple `Fired` outcomes for the same rule+scope within a
   reasonable window correlate into one incident with an incrementing
   `occurrence_count`, not a fresh incident per firing — define and document
   your own correlation window/key since `Docs/SPEC.md` does not pin one
   (same category of necessary judgment call as `MON-001`'s freshness window
   and `MON-002`'s condition grammar — document it, don't silently assume
   it).
4. Bounded evidence: incidents reference bounded evidence snapshots (from
   `MON-002`'s evaluation outcome and the underlying samples), never an
   unbounded/unlimited evidence blob.
5. Assignment: an incident can be assigned to a user or agent identity
   (opaque string at this milestone, same posture as `MON-002`'s
   `rule.creator` — no real identity/auth model exists yet).
6. Timeline: every state transition and assignment change is recorded in an
   append-only timeline, not overwritten.
7. Verification window: `Verifying` -> `Resolved` requires every check to
   pass for a real, tested observation window (time-based, fake-clock
   tested) — not a single instantaneous check.
8. Reopen/close: `Resolved` -> `Open` only within a documented reopen
   policy window; `Resolved` -> `Closed` via retention/policy, both tested.
9. Work-intent emission: a `Fired`/`MissingDataAlert` transition into
   `Open`/`Investigating` emits a work-intent record (per `Docs/SPEC.md` §3's
   work-intent fields: `work_intent_id`, incident, requested capability,
   bounded ...) — emission only, this node does not deliver it anywhere.
10. Real tests: every state-machine edge exercised (including the two
    branches out of `Investigating`, the two out of `WaitingApproval`, the
    two out of `Executing`, the two out of `Verifying`, the two out of
    `Resolved`); correlation test (repeated fires within/outside the window);
    bounded-evidence test; timeline append-only test; verification-window
    test (fake clock); reopen-within-policy vs. reopen-after-policy test;
    work-intent emission test (record shape, not delivery).
11. `cargo build/fmt/clippy/test --workspace` passes across all crates.
12. Worker handoff at `Docs/graph/handoffs/INC-001-1.md`.
