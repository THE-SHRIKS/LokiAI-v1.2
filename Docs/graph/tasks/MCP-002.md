# Task Packet — `MCP-002 Scoped device/workspace/incident read and diagnostic tools`

Packet status: `accepted` | Graph status: `ready` — dispatching
Starting revision: `776c946` (branch `LokiAI-v1.2`, pushed)

## 1. Objective

Read-only MCP tools/resources in `services/mcp-server` (extend `MCP-001`'s
existing server, not a new package) exposing scoped device/workspace/incident
data to a connected agent client: authorized device listing, bounded health
evidence with correlation and freshness, per `Docs/SPEC.md` AS-005 ("connected
MCP client lists authorized devices and reads bounded health evidence with
correlation and freshness"). Read-only only — no flash/build/approval tools
here (that is `MCP-003`, blocked on `APR-001`/`JOB-001`'s consumer wiring/
`BLD-001`).

## 2. Dependencies and ownership

`depends_on`: `MCP-001`, `RUN-002`, `CON-002` (all accepted). Writable:
`services/mcp-server/src/**` additions (new modules — do not rewrite
`MCP-001`'s existing `bootstrap.ts`/`server.ts`/`capabilities.ts`; extend
alongside them) + `services/mcp-server/tests/**` additions +
`services/mcp-server/package.json` (dependency additions only, justified per
`AGENTS.md` rule 11). Do not touch `crates/loki-ipc/**` or
`crates/loki-connector-registry/**` directly — this node consumes both, it
does not modify either.

Note: this worktree branches from `776c946`, which already has `CON-002`
(`crates/loki-connector-registry`) and `JOB-001` integrated — both are
available to read from, but this node only needs `CON-002`'s registry/health
surface, not `JOB-001`.

## 3. Required reading

`AGENTS.md`; `Docs/SPEC.md` section defining AS-003–AS-005 (device
discovery/health read flows); `Docs/CONNECTOR_SPEC.md` (health/capability
vocabulary this surfaces); `services/mcp-server/src/{capabilities,server,
correlationId}.ts` (what this extends — read before adding); this node's
Rust counterpart data shapes: `crates/loki-connector-registry/src/{registry,
health,projection}.rs` (the registry this reads from) — since this is a
Node/TypeScript MCP server and the registry is a Rust crate in a separate
process, this node must be honest about how it actually reaches that data:
either a real IPC call through `RUN-002`'s protocol (preferred, since
`RUN-002` is an explicit dependency) or, if no runtime process/consumer
exists yet to answer such a call, an honestly-reported `runtime_unavailable`
result — the same discipline `DSK-002`'s IPC bridge already established
under the same real-world constraint (no fabricated device data ever).

## 4. Deliverables and acceptance criteria

1. A `list_devices` (or equivalently named) MCP tool/resource: returns only
   devices the connected client is authorized to see (workspace/scope
   boundary — if no real auth/workspace scoping exists yet at this milestone
   per the OQ-002/AUTH-001 blocker, this must be explicitly and honestly
   reported as an open scope gap, not silently bypassed by returning
   everything unscoped).
2. A `get_device_health` (or equivalently named) MCP tool/resource: returns
   bounded (size-limited, not unbounded log dump) health evidence for one
   device, including correlation ID and freshness/staleness per `CON-002`'s
   `AggregatedHealthStatus`/health-check timestamps — never fabricated or
   backfilled data for a device with no real evidence.
3. Pagination: listing tools support a bounded page size; no unbounded
   response.
4. Size bounds: no single tool response can be unbounded (a device with a
   huge evidence history must be truncated/paginated, not dumped whole).
5. Truthful "no runtime/no registry available" results distinct from "zero
   devices registered" — no state silently defaults to an empty-but-successful
   response when the underlying call actually failed/is unavailable.
6. Real tests: auth/scope test (a client without an authorized device sees
   nothing for it — even if that boundary is currently a documented stub
   given `AUTH-001`'s block, the *tool's own scoping code path* must exist
   and be tested against whatever scoping primitive is actually available
   today), pagination test (page size bound honored, no unbounded page),
   response-size test (a large evidence set is bounded not dumped),
   malformed-request tests (matching `MCP-001`'s existing error-handling
   discipline).
7. `pnpm run verify` (or at minimum `services/mcp-server`'s own build/lint/
   typecheck/test) passes; if it touches the Rust side at all (it shouldn't,
   per the writable-scope above), `cargo build/fmt/clippy/test --workspace`
   must also pass.
8. Worker handoff at `Docs/graph/handoffs/MCP-002-1.md`.

packet expects to be surfaced honestly (§4.1/§4.5), not silently invented.

## 7. Stop conditions

`NEEDS_REPLAN` if exposing real device data from `CON-002`'s registry to an
MCP client genuinely requires a runtime host process (`RUN-003`) that does
not exist yet at this milestone in a way that makes this node's own
acceptance criteria unverifiable except via a stub — report exactly what's
missing (the same honest-gap discipline `DSK-002` used for
`runtime_unavailable`) rather than inventing a working data path that
isn't real. `BLOCKED_DEPENDENCY` if `CON-002`'s public API cannot actually
be reached from a Node/TypeScript process without an as-yet-nonexistent IPC
surface this node is not scoped to build.
