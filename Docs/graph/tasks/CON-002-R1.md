## 1. Objective

Replace `loki-connector-registry`'s mock-era candidate/identity handling — which
today mints a `DeviceId` directly from a provisional candidate string
(`crates/loki-connector-registry/src/discovery.rs` lines ~145 and ~171) — with
real candidate ingestion, identify-by-candidate against the accepted Connector
Identity Protocol v1.0.0 (`loki_connectors_sdk::identity`), stable-identity
reconciliation across candidates/cycles, and explicit, distinguishable
busy/permission/disconnect outcomes, so no provisional locator or connector-ID
string can be reported as stable device identity.

  - Current `discovery.rs` (mock-era) has exactly one candidate source: "each

    duplicate/reconnect scenarios at all.

    The correct reading (stated explicitly so it is not silently repeated as

    treated as the final stable identity the way the current code does.
  - **Architectural gap, flagged not silently resolved**: no existing type in
    `loki-connectors-sdk` (`StageOutcome`/`StageEvidence`) lets a connector's
    `identify` call return a typed `TransportCandidate` or
    `IdentityConfidence`/fingerprint material — only a free-text summary
    string. This node is confined to `loki-connector-registry` ownership and
    must NOT touch `loki-connectors-sdk`. If implementation genuinely cannot
    proceed without such a change, STOP and return `NEEDS_REPLAN` (see
    Section 12) — do not invent an undocumented free-text convention to route
    around it.

## 6. Deliverables

1. A candidate-sourcing abstraction in `discovery.rs` that accepts one or more
   `loki_connectors_sdk::identity::TransportCandidate` values per registered
   connector (injected by the caller, e.g. a trait or closure), replacing the
   current one-candidate-per-connector-ID shortcut.
2. Identify-by-candidate: for each candidate, run the connector's `identify`
   capability via the existing `run_operation`/`LifecycleOutcome` path
   (unchanged), then interpret the result into a real `IdentityProbeResult`
   (`Verified`/`Unknown`/`Partial`/`Ambiguous`/`Conflicting`) instead of
   directly minting a `DeviceId` from the candidate string.
3. Stable-identity reconciliation: registry-level state keyed on
   `PublicDeviceIdentity::device_id()`, so a reconnect (new candidate, same
   resolved digest) is recognized as the same device, and duplicate
   candidates within one cycle resolving to the same digest are not
   double-reported.
4. Explicit, distinguishable busy/permission/disconnect outcomes on
   `DiscoveryOutcome` (or its replacement), with the classification
   convention documented in code (module doc) and in the handoff.
5. Updated `registry.rs` call sites (`run_discovery_cycle`, `identify_one`)
   using the new candidate/identity/reconciliation flow.
6. Updated `tests/support/mod.rs` test double extended to produce multiple
   candidates and busy/permission/disconnect-shaped failures on demand
   (mirroring the existing `Behavior`/`HealthBehavior` pattern already in the
   file), still real trait dispatch — not a hand-rolled fake.
7. Real tests per Section 8.
8. Worker handoff, explicitly recording: (a) which `IdentityConfidence`
   handling choice was made and why it is not a silent threshold decision;
   (b) confirmation this node never parses `IdentityProbeResult` from
   untrusted wire data (or, if it does, why and how authenticity is
   independently established); (c) the exact busy/permission/disconnect
   classification convention chosen.

## 7. Acceptance criteria

- [ ] No candidate-derived string (COM port, connector ID, ephemeral
      `candidate_id`) is ever reported as a device's stable identity; only a
      `PublicDeviceIdentity` derived through `IdentityProbeResult::verified`
      is.
- [ ] Two candidates that resolve to the same fingerprint digest reconcile to
      one stable device, not two.
- [ ] A candidate that disappears between cycles does not retain a live
      "verified" status indefinitely without new evidence.
- [ ] Busy, permission-denied, and disconnected outcomes are distinguishable
      from each other and from a generic identify failure.
- [ ] Ambiguous/conflicting evidence for one candidate fails closed (no
      `PublicDeviceIdentity` produced).
- [ ] `IdentityConfidence` handling is an explicit, documented choice, not a
      threshold silently invented mid-implementation.
- [ ] This node states explicitly whether it ever constructs
      `IdentityProbeResult` from untrusted wire data, and if so, how
      authenticity is established beyond shape validation.
- [ ] No prohibited security or architecture boundary is weakened (raw
      sensitive locator still never reaches default logging/serialization).
- [ ] No unrelated files change; `crates/loki-connectors-sdk/**` untouched.
- [ ] Concurrent registry access (register/deregister/discover/reconcile)
      does not corrupt reconciliation state.

## 9. Known open questions — do not resolve silently

1. **No minimum `IdentityConfidence` threshold policy exists yet**
   (`CON-ID-CONTRACT-001-2.md` §6). `IdentityProbeResult::verified()` accepts
   any confidence level including `Weak`. State what this node does and flag
   the policy gap for a future decision node if the chosen behavior is only a
   stopgap — do not invent a threshold as if already decided.
2. **`loki_connectors_sdk::identity` validates wire-data shape only**, not
   independent HMAC authenticity (`CON-ID-CONTRACT-001-2.md` §6). State
   explicitly whether/how this node crosses an untrusted-wire boundary. Given
   connectors are in-process trait objects with no `loki-ipc` dependency, this
   node likely never parses `IdentityProbeResult` from untrusted wire/JSON at
   all — state this as an explicit architectural fact, not an assumption.

## 10. Risks and safety

- Risk level: `high` — identity/security boundary; reconciliation logic that
  is wrong in either direction (over-merging or under-merging) has real
  product-safety consequences for later enrollment/consequential operations.
- Failure modes: incorrect merge of two distinct physical devices into one
  identity; failure to recognize a genuine reconnect; silent adoption of an
  undecided confidence-threshold policy.
- Rollback/recovery: no persisted state yet touched by this node (in-memory
  registry only); revert is a code revert.
- Data/secret impact: `installation_key` for `DeviceIdentityEvidence::new`
  must be supplied by the caller — this node does not generate, store, or
  load it.
- Device impact: none — no device I/O, matches `CON-002`'s established
  precedent.
