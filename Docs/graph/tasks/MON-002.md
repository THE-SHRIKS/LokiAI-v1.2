## 1. Objective

Versioned monitoring-rule evaluation in `crates/loki-monitoring` (extend the
existing crate — this node owns rule/evaluation logic on top of `MON-001`'s
ingestion pipeline, not a new crate): rules with scope selector, required
signals, condition, window, debounce/cooldown, severity, enabled state, and
explicit missing-data behavior, per `Docs/SPEC.md` §3.6 and `FR-MON-002`.
Deterministic evaluation only — no fuzzy/inferred triggering; a rule fires
because its condition was actually met against real ingested samples within
its window, never guessed.

## 4. Deliverables and acceptance criteria

1. Rule model: `rule_id`, version, workspace, scope selector, required
   signals, condition, window, debounce/cooldown, severity, enabled state,
   explicit missing-data behavior, creator, timestamps — matching
   `Docs/SPEC.md` §3.6's field list exactly; do not invent extra fields or
   silently drop any of these.
2. Deterministic window/condition evaluation: given a fixed set of ingested
   samples and a fixed rule, the fire/no-fire outcome is reproducible (same
   inputs -> same outcome, tested with a fake clock the same way `MON-001`
   used one, not real wall-clock timing).
3. Debounce/cooldown: a rule that keeps meeting its condition does not
   re-fire on every single sample — debounce (must stay met for a duration
   before first firing) and cooldown (suppressed for a duration after
   firing) are both real, tested, distinct behaviors, not conflated into one.
4. Missing-data behavior: a rule whose required signal goes stale/absent
   (via `MON-001`'s `FreshnessTracker`) behaves per its own configured
   missing-data setting — explicitly one of "treat as met," "treat as not
   met," or "fire its own missing-data alert," whichever the rule declares —
   never silently defaulting to one without the rule saying so.
5. Rule versioning: changing a rule's definition does not retroactively
   reinterpret already-evaluated history; an old evaluation record stays
   attributed to the rule version that actually produced it.
6. Restart: enabled rules and their debounce/cooldown state behave sanely
   across a process restart — follow `MON-001`'s own established pattern
   (durable data survives via the store; in-memory working state honestly
   resets rather than being fabricated, unless there's a real reason a given
   piece of rule state must itself be persisted — state which explicitly).
7. Real tests: deterministic evaluation (fixed inputs, fixed outcome, fake
   clock), debounce proven distinct from cooldown, each of the declared
   missing-data behaviors actually exercised (not just one), rule-version
   attribution test (change a rule, confirm old evaluation records keep
   their original version), restart test.
8. `cargo build/fmt/clippy/test --workspace` passes across all crates.
9. Worker handoff at `Docs/graph/handoffs/MON-002-1.md`.
