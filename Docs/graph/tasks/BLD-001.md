# Task Packet — `BLD-001 Contained build executor`

Packet status: `accepted` | Graph status: `ready` — dispatching
Starting revision: `776c946` (branch `LokiAI-v1.2`, pushed)

## 1. Objective

New crate `crates/loki-build-executor` (or similar — name it clearly, record
the choice): a separate, least-privilege build executor per
`Docs/BUILD_EXECUTION.md` (read in full — it is the normative safety boundary
for this node, not optional background). This is one of the highest-risk
nodes in Part One: it exists specifically so untrusted repository/build code
never runs with LokiAI Runtime's own privileges. Read `Docs/BUILD_EXECUTION.md`
section 7 ("`BLD-001` must prove...") as this packet's real acceptance bar —
it is more demanding than the deliverables list below, which summarizes it.

`depends_on`: `JOB-001`, `CON-001`, `RUN-002` (all accepted). Writable: new

## 4. Deliverables and acceptance criteria

1. Build recipe contract (`Docs/BUILD_EXECUTION.md` §3): a typed, versioned
   recipe struct — recipe/connector ID+version, supported target/artifact
   types, exact toolchain identity + expected digest, a fixed argument
   template with typed allowlisted substitutions (never a free-form command
   string), source input roots with read/write mode, allowlisted environment
   variables with secret classification, expected output paths/formats/size
   bounds, resource limits (CPU/memory/process-count/disk/wall-clock),
   network policy defaulting to denied, redaction rules. No MCP/UI-suppliable
   field can smuggle an arbitrary executable/command/script/URL/env var/
   output path — this must be structurally true of the types, not just
   documented.
2. Windows containment (`Docs/BUILD_EXECUTION.md` §4): the executor launches
   as a **separate process** (not an in-process sandbox simulation) using
   real Windows AppContainer isolation + Job Object limits — low integrity,
   no network capability, no access to credential stores/LokiAI database/
   runtime named pipe/signing material/USB-serial/clipboard/UI/registry/home
   directories/unrelated repos, read-only snapshot+toolchain access, write
   access only to a fresh per-job scratch/output directory, kill-on-close
   Job Object for the whole process tree, bounded stdout/stderr/files/
   process-count/CPU/memory/disk/duration, headless (no Win32k/UI where
   compatible). Containment startup must be **fail-closed**: if the sandbox
   profile or tool-identity verification cannot be established, the build
   stage must not be marked running — it must fail closed, never silently
   run unsandboxed.
3. Build stages (`Docs/BUILD_EXECUTION.md` §5): requested -> source revision
   resolved -> recipe/target resolved -> policy decision -> source snapshot
   created -> toolchain digest verified -> sandbox created and attested ->
   build executed with limits -> outputs quarantined -> artifact format/
   size/target validated -> digest+provenance recorded -> artifact
   registered -> sandbox teardown and audit. A successful build creates an
   artifact; it must not authorize flash/deployment (those are separate,
   later stages/nodes with separate identities — do not conflate them here).
4. Provenance record (`Docs/BUILD_EXECUTION.md` §6): source revision+dirty
   state, recipe/connector/toolchain/executor digests, normalized
   parameters, dependency lockfile digests, start/end time, resource result,
   output digest, reproducibility result where applicable, requester, job/
   correlation IDs, redacted log references. Build output must be treated as
   untrusted until validated outside the sandbox (type/size/target
   compatibility/digest) — an artifact label supplied by the build itself
   must never be able to alter policy or select a physical target.
5. Real tests proving `Docs/BUILD_EXECUTION.md` §7's actual list — this is
   the real bar, not a paraphrase:
   - a build can read only its granted snapshot/toolchain and write only its
     own output (attempt to read/write outside → denied, tested);
   - attempts to access LokiAI secrets/database/named pipe/arbitrary files/
     network/UI/USB-serial/another build's directory all fail (tested, not
     asserted from documentation);
   - child processes stay inside the resource/termination boundary (a
     forked/spawned grandchild cannot escape the Job Object — tested);
   - timeout, output flood, process-bomb, disk-exhaustion, malformed-output,
     and executor-crash scenarios each produce a bounded failure plus a
     durable job-reconciliation outcome (via `JOB-001`'s `quarantine`/
     `outcome-unknown` semantics — never a false "succeeded"), each actually
     exercised, not just described;
   - a tool/recipe/source change invalidates cached provenance and any bound
     approval (tested);
   - the same declared input is reproducible where the toolchain supports it
     (tested for at least one real toolchain, or explicitly and honestly
     scoped down if no real toolchain is available at this milestone —
     report the gap, don't fabricate a reproducibility result);
   - no artifact reaches the (future) artifact store before external
     validation succeeds (tested at this crate's own boundary, since
     `ART-001` — the artifact store itself — is a later node).
6. `cargo build/fmt/clippy/test --workspace` passes across all crates.
7. Worker handoff at `Docs/graph/handoffs/BLD-001-1.md`, with an explicit,
   honest accounting in Section 6 (Security/privacy/device safety) of
   exactly which of the above containment properties were verified by a
   real adversarial test on this Windows machine vs. which are structurally
   enforced by the type system vs. which remain an open gap — do not let any
   of the three categories blur into another.

## 5. Human gate

None to *build* this node (no consequential/device operation is performed by
building the executor itself — it runs no real device flash). However, this
node's self-report alone is **not sufficient for acceptance** given its
safety-boundary role: before this orchestrator marks `BLD-001` `accepted`,
an independent `loki-security-reviewer` pass is required against the actual
containment implementation (not the handoff's narrative), specifically
checking for AppContainer/Job Object bypass, fail-open startup paths, and
any MCP/UI-suppliable field that could smuggle an arbitrary command. Record
that review's outcome before acceptance.

## 7. Stop conditions

`NEEDS_REPLAN` if a required vendor/toolchain interaction genuinely cannot
run under the accepted containment profile — per `Docs/BUILD_EXECUTION.md`
§2, that build capability is unavailable until an ADR approves a different,
equally reviewed executor (e.g. a signed remote ephemeral build service);
LokiAI must not fall back to an ordinary unrestricted child process. Report
the boundary rather than weakening containment to make a test pass.
`NEEDS_REPLAN` if real Windows AppContainer/Job Object process-launch APIs
cannot be exercised at all in this environment (e.g. missing OS
privilege/feature) — report exactly what was and wasn't possible to verify
rather than simulating containment with an in-process fake and calling it
proven. `BLOCKED_DEPENDENCY` if `JOB-001`'s `quarantine`/`outcome-unknown`
states cannot actually represent one of the required crash/ambiguous-outcome
scenarios above without a change to `crates/loki-jobs` this node is not
scoped to make — report exactly what's missing.
