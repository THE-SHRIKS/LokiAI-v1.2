## 6. Security, privacy, and device safety

This node's entire purpose is security posture — summary, not a footnote:

- `webPreferences`: `contextIsolation: true`, `nodeIntegration`/`InSubFrames`/
  `InWorker: false`, `sandbox: true`, `webSecurity: true`,
  `allowRunningInsecureContent: false`, `webviewTag: false` — all asserted by a
  real test reading the actual returned object, not re-typed
- No remote module (verified by dependency-graph inspection AND a source scan
  of the actual shipped main/preload files)
- Permissions and `window.open()` denied by default, synchronously and
  asynchronously
- Navigation restricted to same-origin (http/s) or the packaged renderer's own
  directory (`file:`); a different host/scheme/port, or a `file:` path outside
  the renderer directory, is denied; malformed URLs denied, not thrown
- CSP: production has no `unsafe-inline`/`unsafe-eval`; only Google Fonts
  origins are allowed beyond `'self'`, because the **unmodified** renderer HTML
  references them directly and DSK-001 must not touch renderer source; the
  relaxed dev-only CSP is structurally unreachable from a packaged build
  (`electron:package` never sets the env var that selects it)
- New dependencies: `electron` (43.4.0, exact `TECH_STACK.md` match),
  `@electron-forge/cli`/`plugin-fuses`, `@electron/fuses` — standard packaging
  toolchain, not independently re-license-checked this pass (recommend at
  integration)

## 7. Decisions and assumptions

- **Honest empty/error state, not a blank window**: when the renderer build is
  missing, `rendererTarget.cts`/`index.cts` load a data-URL error page instead
  of silently loading nothing — direct application of `AGENTS.md`'s "expose an
  honest loading, empty, disconnected, or error state" rule.
- **`.cts`/CommonJS for main/preload, not ESM** — documented rationale in
  `electron/tsconfig.json`: sidesteps real ESM-preload edge cases across
  Electron versions; not a shortcut, a stated tradeoff.
- **`pnpm-workspace.yaml` `overrides` for `@electron/node-gyp`** — real
  supply-chain-guard blocker, well-justified inline, verified to have zero
  runtime effect (no native addons built here).

### 7a. Known gap, not silently worked around: `pnpm run electron:package` itself

Electron Forge's own preflight check refuses to package against pnpm's default
"isolated" `node_modules` layout — a standard, widely-documented Electron+pnpm
friction point. The standard fix (`node-linker=hoisted` in `.npmrc`) does **not**
take effect on this repo's pinned pnpm 11.21.0: a fresh `rm -rf node_modules &&
pnpm install` with that setting present still produces an isolated layout
(confirmed via `node_modules/.modules.yaml` and by checking whether
`node_modules/electron` is a real directory or a `.pnpm`-store symlink — it
stayed a symlink). Root cause not conclusively identified; a `pnpm install
--node-linker=hoisted` CLI-flag attempt hung indefinitely (killed after ~10
minutes of unchanging CPU time — likely a Windows file-handle lock from an
Electron process I had running during testing, not necessarily pnpm's fault).

**The application itself is proven, independent of this gap**: `npx
electron-forge package` resolves through plain npm instead of pnpm and doesn't
hit the preflight check at all. It produced the exact same `out/LokiAI-win32-x64/
lokiai.exe` that I then launched, screenshotted-in-spirit via window-title/PID
evidence, and verified end-to-end (Section 4). The gap is specifically that
**`pnpm run electron:package` — the packet-intended, reproducible command — does
not currently work**, not that the packaging or the app is broken.

Documented in `.npmrc` itself so it isn't lost. Whoever next touches packaging
(a `DSK-001-R1` revision, or `PKG-001`) should resolve this properly — do not
adopt `npx` as a standing substitute for the pnpm-native command without
recording that as its own decision.
