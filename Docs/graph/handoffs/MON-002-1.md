## 1. Outcome

`crates/loki-monitoring` now has a versioned monitoring-rule model and a
deterministic evaluation engine built on `MON-001`'s ingestion pipeline. A
`MonitoringRule` carries `Docs/SPEC.md` §3.6's exact field list (rule_id,
version, workspace, scope selector, required signals, condition, window,
debounce/cooldown, severity, enabled, missing-data behavior, creator,
timestamps) — nothing invented, nothing dropped. `RuleEvaluator` evaluates a
rule against already-ingested samples and `MON-001`'s `FreshnessTracker`
state with a fake-clock-only, side-effect-free state machine: debounce (must
stay met before the *first* fire) and cooldown (suppressed for a duration
*after* a fire) are two independently testable, non-conflated concepts; a
rule's own declared `MissingDataBehavior` (treat-as-met, treat-as-not-met, or
its own distinct missing-data alert) governs what happens when a required
signal goes stale/absent, never silently defaulting. `RuleStore` persists
every rule version as an immutable, append-only row and every evaluation
outcome permanently attributed to the exact rule version that produced it,
in a second `rusqlite::Connection` into the *same* self-contained SQLite
database `MON-001`'s `SqliteTelemetryStore` already opens — no edit to
`crate::store` or any other `MON-001` file, per this node's writable-scope
boundary. In-memory debounce/cooldown streak state honestly resets on
restart (a fresh `RuleEvaluator`), matching `MON-001`'s established pattern
for durable-data-survives/in-memory-state-resets. `crate::rule::ScopeSelector`
matches already-ingested `DeviceId`s mechanically (not a real device/
workspace authorization decision), which is how this node's scope-selector
tests stay fully deterministic without needing the still-`blocked`
`AUTH-001`/`ENR-001` device-ownership model — resolving this node's own stop
condition rather than triggering it. The full 5-crate workspace builds,
formats, lints clean under `-D warnings`, and all tests pass together (75
`loki-monitoring` unit tests plus 9 external test files for this crate
alone — 4 pre-existing `MON-001` plus 5 new `MON-002` files totalling 20 new
black-box tests; 253 tests workspace-wide, all green).

## 7. Decisions and assumptions

- **Condition grammar: a single-signal threshold comparison
  (`ComparisonOperator` + `f64` threshold), not an open-ended expression
  language.** `Docs/SPEC.md` §3.6 says only "condition" — no grammar is
  defined. A fixed, exhaustively-matchable comparison satisfies "no fuzzy/
  inferred triggering" without speculative scope growth; documented in
  `rule.rs`'s module doc as this node's own necessary design decision (same
  category as `MON-001`'s undefined freshness-window default).
- **`workspace` is an opaque, caller-supplied string, not a resolved
  identity — and `ScopeSelector` matches `DeviceId`s mechanically, not via
  authorization.** This directly addresses the packet's stop condition
  (§7): no real device/workspace model exists yet (`AUTH-001`/`ENR-001` both
  `blocked` per `Docs/graph/TASK_GRAPH.md`, confirmed by re-reading it
  directly rather than trusting the packet's own characterization).
  `ScopeSelector::matches` only asks "is this one of the device ids this
  rule's author listed against already-ingested samples" — a plain
  structural comparison, the same kind of thing `DeviceId`'s own doc already
  describes as in-scope today. This makes every scope-selector test fully
  deterministic and self-contained without fabricating a workspace/device-
  ownership model, resolving the stop condition rather than triggering
  `NEEDS_REPLAN`. Documented at length in `rule.rs`'s `ScopeSelector` doc
  comment so a reviewer can independently check this reasoning.
- **Debounce/cooldown semantics: debounce gates only the *first* fire of a
  continuous streak; cooldown gates *every* fire thereafter, independently.**
  Once a streak has satisfied debounce once, it does not need to re-satisfy
  it again as long as the streak never breaks — only cooldown gates
  subsequent fires. This is a deliberate, documented design choice
  (`evaluate.rs`'s module doc spells out the exact state machine and why),
  since `Docs/SPEC.md` §3.6 does not define the interaction between the two
  beyond naming them separately. Chosen because it keeps the two concepts
  observably distinct and testable (the packet's explicit requirement)
  rather than picking a interaction rule that would make one field able to
  silently absorb the other's effect.
- **`RuleStore` is a second `rusqlite::Connection` into `crate::store`'s
  self-contained database, not an edit to `store.rs`.** See §5 for the full
  mechanical reasoning; proven to actually work (not just asserted) by a
  dedicated test.
- **`crate::validate`'s list-encoding helpers are a second copy of
  `crate::store`'s private `encode_string_list`/`decode_string_list`,** not
  a reuse of `store.rs`'s existing private functions, because `store.rs` is
  outside this node's writable scope to edit (even to change a function's
  visibility). Flagged as intentional duplication, not an oversight — the
  alternative (editing `store.rs`) was the one thing explicitly forbidden.
- **In-memory debounce/cooldown streak state does not survive restart;
  durable rule definitions/evaluation history do.** Directly follows
  `MON-001`'s established pattern (`Docs/graph/handoffs/MON-001-1.md` §7)
  and is explicitly named as the required approach in this node's own
  packet (§4 Deliverable 6). Tested by
  `tests/rule_restart.rs::in_memory_debounce_state_honestly_resets_after_a_restart_it_is_not_fabricated`.

No unresolved assumption here changes this node's own acceptance criteria —
all 9 deliverables pass as written. The condition-grammar and workspace/
scope-selector decisions are the two most likely to warrant orchestrator
review; see §8.
