## 1. Outcome

New crate `crates/loki-connector-registry` implements the connector registry
plus discovery/identity/support/capability/health orchestration this node's
packet requires. It registers/deregisters `loki-connectors-sdk::Connector`
instances behind a concurrency-safe map, runs a real discovery cycle by
invoking the SDK's own `identify`-capability preflight->execute->verify
lifecycle against each registered connector (never fabricating identity from
anything other than a genuinely succeeded, independently-verified outcome),
runs health-check cycles with an honest aggregation rule that never masks an
unhealthy connector, and projects each connector's declared capability risk
and per-target support-tier certification verbatim from its own manifest. All
of it is exercised against a real `Connector` trait implementation (this
crate's own `TestConnector` test double — see Section 7 for why it is not
`CON-001`'s own `MockConnector`), not hand-rolled fake discovery/health data.

## 7. Decisions and assumptions

1. **The packet says "using CON-001's conformance mock"; I did not literally
   import `CON-001`'s `MockConnector`.** `MockConnector` lives in
   `crates/loki-connectors-sdk/tests/support/mod.rs` and is deliberately
   private to that crate's own test binary — its own task packet
   (`CON-001` Deliverable 4) scopes it to "used only by this crate's own
   tests," and this crate's own packet explicitly forbids touching
   `crates/loki-connectors-sdk` at all (even to add a `pub`/feature-gated
   export). Cargo's own module system makes a `tests/`-only item
   uncrossable from another crate regardless. I built this crate's own
   `TestConnector` (`tests/support/mod.rs`), a real
   `loki_connectors_sdk::Connector` trait implementation — the same shape
   `MockConnector` is, exercised the same way (real `preflight`/`execute`/
   `verify`/`health_check` dispatch through the SDK's own `run_operation`,
   never a hand-rolled fake that skips the trait). I read this as the
   correct, honest resolution of the packet's intent ("real discover/
   identify against the mock, not a hand-rolled fake" — the *contrast* the
   packet draws is with fabricated data, not with which specific mock
   struct is used) rather than a deviation that changes what's actually
   being proven. Flagged explicitly here per `AGENTS.md`'s "state any
   necessary assumption in the handoff" — if the orchestrator disagrees
   with this reading, the fix is narrow (either accept this crate's own
   `TestConnector` as satisfying the intent, or open a follow-up to make
   `CON-001`'s `MockConnector` a `#[cfg(feature = "test-util")]` public
   export for `CON-002` to import instead).

2. **No `loki-ipc` dependency.** The packet names `RUN-002`'s IPC as
   available "for whatever transport discovery needs." This node's actual
   scope — discovery/health orchestration against an already-registered,
   already-transport-wired `Connector` trait object — never needs to open a
   transport of its own; `loki-connectors-sdk`'s own design (see
   `operation.rs`'s module doc) puts transport wiring privately inside each
   connector implementation, not in anything this registry touches
   directly. Adding `loki-ipc` as an unused dependency would violate
   `AGENTS.md` rule 11. Documented in `src/lib.rs`'s module doc and here for
   explicit orchestrator review — if a future node needs this registry to
   reach across the desktop-shell/runtime IPC boundary, that is new scope,
   not something silently missing from this one.

3. **`identify` is invoked through the SDK's generic
   preflight->execute->verify lifecycle, not a bespoke "discover" method.**
   `loki_connectors_sdk::Connector` has no `probe`/`discover`/`identify`
   method of its own — `CON-001`'s own `operation.rs` module doc says
   identity-evidence modeling is explicitly `CON-002` scope, and `identify`
   is already one of `Docs/CONNECTOR_SPEC.md` §6's named capability ids. I
   treated `identify` as invoked the same way every other capability is
   (§8's operation contract applies uniformly), which lets this crate reuse
   the SDK's own lifecycle runner and success rule
   (`LifecycleOutcome::succeeded()`) exactly rather than inventing a second,
   parallel notion of "did this connector actually succeed." See
   `discovery.rs`'s module doc for the full reasoning, including why there
   is no separate transport-"probe" step in this node (no real transport
   exists to probe yet at this milestone — `CON-003` is blocked on
   `OQ-001`).

4. **Health aggregation rule (`AggregatedHealthStatus::from_report`) is this
   crate's own documented choice**, since `Docs/CONNECTOR_SPEC.md` §7 defines
   per-entry status but not a connector-level folding rule. Any `Failed`
   entry outweighs everything else (Unhealthy); `Warning`/`Interrupted`
   without a `Failed` is Degraded; an empty report or an all-`Unavailable`
   report is Unavailable, never Healthy (absence of evidence is not
   evidence of health). Flagged for reviewer attention in Section 8.

## 8. Review focus

1. **Section 7, decision 1** — whether `TestConnector` (this crate's own
   test double) genuinely satisfies the packet's "using CON-001's
   conformance mock" language, or whether the orchestrator wants a follow-up
   to expose `CON-001`'s `MockConnector` behind a `test-util` feature for
   `CON-002` (and future connector-consuming crates) to import directly
   instead of each maintaining its own.
2. **`health.rs`'s `AggregatedHealthStatus::from_report` rule** (decision 4
   above) — confirm the precedence (`Failed` > `Warning`/`Interrupted` >
   `Passed`-only > empty/`Unavailable`-only) matches what downstream
   consumers (future UI/MCP surfaces) will actually expect, since
   `Docs/CONNECTOR_SPEC.md` does not pin this itself.
3. **`registry.rs`'s locking shape** (`RwLock<HashMap<ConnectorId,
   Arc<Entry>>>` + per-entry `Mutex<Box<dyn Connector>>`) — the concurrency
   test proves no state corruption for the scenario it exercises (mixed
   register/deregister/list/health-cycle across 50 connectors), but a
   reviewer should confirm the snapshot-then-release-lock pattern in
   `snapshot()` is the right tradeoff (a `register`/`deregister` can
   interleave with an in-flight discovery/health cycle's snapshot, so a
   cycle might act on a connector that was deregistered moments after the
   snapshot was taken — this crate treats that as acceptable "operated on
   a connector that existed at cycle-start" semantics, not a bug, but it is
   worth an explicit second opinion).
4. **`discovery.rs`'s `CandidateId::from_connector_id`** — this milestone's
   candidate source (each already-registered connector instance is itself
   the one candidate to identify) is explicitly a placeholder honest about
   having no real transport-probing to draw candidates from yet; confirm
   this does not quietly become load-bearing beyond this milestone once
   `CON-003` needs real multi-candidate transport probing.
