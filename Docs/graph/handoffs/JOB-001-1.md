## 1. Outcome

`crates/loki-jobs` now provides a durable job/lease engine (`JobEngine`) built
directly on `DAT-001`'s existing `loki_storage::jobs::JobRepository` and its
15-value `JobState` vocabulary — no new SQLite table/migration was added (see
§7 for why, and why that is a deliberate, in-scope choice rather than a
`BLOCKED_DEPENDENCY`). The engine drives `queued -> preflight -> executing ->
testing -> succeeded/failed`, with `outcome-unknown` as an explicit
quarantine state reachable both from an ambiguous in-flight call and
automatically from `JobEngine::reconcile()` at startup (the crash-mid-job
case). Idempotent submission, cooperative cancel, explicit restart of a
`failed`/`outcome-unknown` job, and an in-memory per-device lease
(acquire/renew/release, exclusive, reclaimable after expiry) are all
implemented and covered by real tests against a real in-memory SQLite
database. The full 5-crate workspace builds, formats, lints clean, and all
tests pass together.

## 7. Decisions and assumptions

- **No new SQLite table/migration was added, despite the task packet naming
  that as a possible path** ("a new `jobs`-adjacent table/migration if
  needed"). Reason: this node's writable scope is `crates/loki-jobs/**` plus
  one `Cargo.toml` members line, and explicitly excludes
  `crates/loki-storage/**` except for adding a *migration file*. But
  `loki_storage::Storage`'s SQLite connection is `pub(crate)` to
  `loki-storage` only — any new table's repository *code* (the trait impl
  that would actually read/write it) would have to live in
  `crates/loki-storage/src/**`, which this node cannot touch. Registering a
  new migration file also requires an edit to
  `crates/loki-storage/src/migrations.rs`'s embedded `MIGRATIONS` array (an
  `src/**` file), so even "just add a migration file" cannot be done in
  isolation. Rather than reshape `DAT-001`'s schema/repository code
  unilaterally (an explicit stop condition in the task packet, §7: "report
  exactly what's missing rather than reshaping `DAT-001`'s schema
  unilaterally"), I designed the lease as in-memory, per-process state
  instead: `loki_storage::states::JobState` already has no "leased" state of
  its own (leasing is orthogonal device-exclusivity bookkeeping, not a job
  lifecycle stage), and the crash-recovery property the packet actually asks
  for ("a lease that isn't renewed is reclaimable," "crash-mid-job leaves a
  quarantined state") is fully satisfiable — and is real-tested — via
  `JobEngine::reconcile()`: a freshly started engine's lease table is always
  empty, so it correctly treats every job a prior process left in a
  non-terminal in-flight state as unverifiable and quarantines it. This is
  not a workaround; it is arguably the more correct design for "a process
  crashed" (no in-memory state survives a crash, full stop), and it keeps
  ownership boundaries clean. Flagging this explicitly per `AGENTS.md`
  task-hygiene guidance ("state any necessary assumption in the handoff")
  rather than hiding it.
- This engine drives only a bounded subset of `loki_storage::states::JobState`'s
  15-value vocabulary (`queued`, `preflight`, `executing`, `testing`,
  `succeeded`, `failed`, `cancelled`, `outcome-unknown`) — `policy-check`/
  `waiting-approval` (`APR-001`), `restarting`/`observing`/`rollback-*`
  (`Docs/SPEC.md` 4.8 Deployment) are out of scope and this engine actively
  rejects any transition into or out of them (tested in
  `transitions.rs::out_of_scope_states_have_no_allowed_transitions_in_either_direction`).
- `JobEngine` owns one injected `Clock` (production: `SystemClock`; tests:
  `FakeClock`) for every timestamp it produces (both `created_at`/
  `updated_at` strings handed to `loki_storage` and lease-expiry
  comparisons), rather than requiring every caller to separately supply a
  matching timestamp on every call. This mirrors `loki_storage`'s own
  "no incidental system-clock reads, inject/validate at the boundary"
  stance while keeping this crate's public API small.
- `restart()` mints a brand-new job ID + idempotency key for the retry
  attempt (caller-supplied, per `crates/loki-storage/src/ids.rs`'s "ID
  minting is a domain-layer decision" convention) rather than reusing the
  failed job's own idempotency key, and carries the source job's
  `correlation_id` forward for traceability. This was not explicit in the
  packet; it is the natural reading of "explicitly restarted" combined with
  `Docs/SPEC.md` 4.7's per-idempotency-key exactly-once guarantee (a restart
  is a deliberate new attempt, not a replay).
