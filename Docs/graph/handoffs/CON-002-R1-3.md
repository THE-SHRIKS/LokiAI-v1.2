## 1. Outcome

Fixes the single Medium security-review finding against `CON-002-R1-2`: a
reachable panic in `crates/loki-connector-registry/src/discovery.rs`'s
`build_identify_request` on a legitimately-sized `candidate_id`.

**Root cause.** `TransportCandidate::new` bounds `candidate_id` to 128 bytes —
the *same* 128-byte bound `OperationId`/`IdempotencyKey`/`DeviceId` enforce on
their own raw input. `build_identify_request` wrapped `candidate_id` as
`"discover-{candidate_id}-{sequence}"` for the operation id and idempotency
key, adding roughly 30 bytes (prefix + dash + up to 20 `u64` digits). Any
`candidate_id` longer than the wrapper's headroom — entirely valid per
`TransportCandidate::new`'s own bound — pushed the wrapped string over
`OperationId`'s bound, and `OperationId::new(...).expect(...)` (and the
equivalent `IdempotencyKey::new(...).expect(...)`) panicked. No existing test
caught this because every test used short literal ids (e.g. `"cand-1"`).

**Fix chosen: option (a) — return a proper failure result, not a panic.**
`build_identify_request` now returns
`Result<OperationRequest, DiscoveryFailureClass>`. On any of the three
possible `ValidationError`s (operation id, idempotency key, or — defensively —
device id, even though a `candidate_id` that actually matches the one used to
build its `TransportCandidate` can never itself exceed `DeviceId`'s identical
128-byte bound), it returns
`Err(DiscoveryFailureClass::CandidateNotAddressable)` instead of panicking.

Option (b) (independently re-bound `ObservedCandidate::candidate_id` to
`128 - len("discover-") - len("-") - 20 = 98` bytes, precisely computed)
was considered and rejected: it would silently narrow what candidate ids this
crate accepts below what its own read-only dependency
(`TransportCandidate::new`) legitimately allows, which is exactly the kind of
undocumented, invented constraint `AGENTS.md` rule 1 and this packet's
Section 9 discipline warn against. Returning an honest failure outcome keeps
`TransportCandidate::new`'s 128-byte bound as the single source of truth for
what a valid `candidate_id` is, and only fails the *addressing* step this
crate itself owns.

## 2. What changed, precisely

- `discovery.rs`:
  - `DiscoveryFailureClass` gained a sixth variant,
    `CandidateNotAddressable` — documented as **not** a connector-reported
    failure (never produced by `DiscoveryFailureClass::classify`, which only
    ever classifies a real `ConnectorError`) and **not** to be read as
    Busy/PermissionDenied/Disconnected/Unsupported/Generic. It means the
    connector's `identify` capability was never invoked for this candidate
    at all, because this registry could not build a well-formed `identify`
    request from it.
  - `build_identify_request` signature changed from
    `fn(&ObservedCandidate) -> OperationRequest` to
    `fn(&ObservedCandidate) -> Result<OperationRequest, DiscoveryFailureClass>`.
    All three `.expect(...)` panics on candidate-derived id construction are
    gone; each converts its `ValidationError` into
    `Err(DiscoveryFailureClass::CandidateNotAddressable)` via a single
    `map_err` closure. (`OperationRequest::new(...)`'s own trailing `.expect`
    was left as-is: given already-valid components its constructor is
    structurally infallible — `Ok` is always returned — so this is not a
    reachable panic; it is now also routed through the same `map_err` for
    defense in depth, at no behavioral cost.)
  - New `pub(crate) fn unaddressable_probe(...)` builds a `CandidateProbe` for
    a candidate that could never be addressed: `lifecycle: None`,
    `evidence: None`, `probe_result: None`,
    `failure_class: Some(CandidateNotAddressable)`.
  - `CandidateProbe.lifecycle` and `DiscoveryOutcome.lifecycle` changed from
    `LifecycleOutcome` to `Option<LifecycleOutcome>` — `None` only in the
    `CandidateNotAddressable` case (the connector was never invoked); every
    other outcome, including every connector-reported failure, still always
    carries `Some(_)`. `interpret_identify_outcome` (only ever called after a
    real lifecycle ran) wraps its `LifecycleOutcome` in `Some(...)` at every
    construction site; its own signature and behavior are otherwise
    unchanged.
  - Module doc gained a short addendum under "Busy/permission/disconnected/
    unsupported classification convention" documenting this sixth case.
  - `build_identify_request`'s own doc comment now explains the exact byte
    math and why this returns `Result` instead of panicking.
- `registry.rs`:
  - `run_discovery_cycle`: for each observed candidate,
    `build_identify_request` is now matched; on `Err(failure_class)`, the
    candidate is turned into an `unaddressable_probe(...)` and the loop moves
    to the next candidate — the connector is never invoked for that one
    candidate, but every other candidate for that connector (and every other
    connector) proceeds normally. The resulting `CandidateProbe` flows into
    `reconcile_connector_probes` exactly like any other probe.
  - `identify_one`: same pattern — on `Err(failure_class)`, builds an
    `unaddressable_probe(...)` instead of running the lifecycle, then still
    goes through `reconcile_connector_probes` and returns
    `Ok(DiscoveryOutcome)` (not a new `RegistryError` variant): this keeps
    `identify_one`'s error type meaning exactly what it already means —
    registry *bookkeeping* failures (`RegistryError::NotFound`) — while the
    *candidate-shape* failure is reported the same honest way
    `run_discovery_cycle` reports it, via `DiscoveryOutcome.failure_class`.
  - Three existing test assertions (`registry.rs`) and four (`tests/
    registry_lifecycle.rs`) that read `.lifecycle.succeeded()` directly were
    updated to `.lifecycle.as_ref().is_some_and(|l| l.succeeded())` to match
    the new `Option<LifecycleOutcome>` type — no assertion's meaning changed;
    every one of those tests uses a short literal candidate id, so
    `lifecycle` is always `Some(_)` there, exactly as before.
- `tests/support/mod.rs`: untouched by this fix (no change was needed there).

1. `a_candidate_id_exactly_at_transportcandidate_s_128_byte_bound_does_not_panic`
   — a 128-byte `candidate_id` (the exact bound `TransportCandidate::new`
   allows). Asserts `build_identify_request` returns
   `Err(DiscoveryFailureClass::CandidateNotAddressable)`, not a panic.
2. `a_candidate_id_far_beyond_the_old_panic_threshold_does_not_panic` — a
   second, independently-constructed 128-byte id (well past the ~117-byte
   threshold the original vulnerable code would have panicked at), same
   assertion, to directly cover the finding's own stated reproduction case.
3. `a_short_candidate_id_still_builds_a_well_formed_request` — a ~20-byte
   candidate id, confirming the fix does not regress the ordinary case:
   `build_identify_request` still returns `Ok(_)` and the built
   `OperationRequest.operation_id` still starts with `"discover-"`.

All three are real, meaningful outcomes (a distinct `Err` variant or a
successful `Ok`), not merely "did not crash" assertions. `two_requests_for_
the_same_candidate_get_distinct_operation_ids` (pre-existing) was updated
only for the new `Result` return type (`.expect(...)`), with its own
assertions unchanged.

## 7. Security and safety notes

- This fix removes a reachable availability bug: a discovery cycle for one
  connector reporting a legitimately-sized candidate could previously bring
  down the whole process via an unwrap-style panic on attacker/environment-
  influenced input length (a candidate id is not user-typed, but is not
  bounded to short values by anything this crate controls either). The fix is
  strictly fail-closed: an unaddressable candidate produces no
  `PublicDeviceIdentity`, no lifecycle run, and a distinctly classified,
  never-misread-as-connector-reported failure outcome.
- No change to `IdentityConfidence` handling, wire-boundary posture, or the
  existing busy/permission/disconnect/unsupported classification convention
  — those remain exactly as `CON-002-R1-2`'s handoff §7 documented. This
  fix only adds a sixth, clearly-separated failure class for "never
  addressed," and never lets it collide with the other five.
- No raw sensitive locator handling changed; no new `Serialize` impl added.
