## 1. Outcome

`crates/loki-monitoring` now provides a bounded telemetry/log ingestion
pipeline: a capacity-bounded ingest buffer with an explicit, tested
drop-oldest policy; per-signal freshness/quality tracking that never treats a
stale signal as current; mechanical sequence-gap detection that reports an
exact missing count and never fabricates backfilled data; a bounded
multi-subscriber event bus (`tokio::sync::broadcast`-based) so a slow or
absent consumer cannot block or memory-balloon the producer; and a durable
SQLite-backed store so ingested samples/logs/gaps survive a simulated process
restart while in-memory working state (buffers, freshness, gap detector)
honestly resets rather than fabricating pre-restart state. `Pipeline` ties
all of this together as the crate's public ingest API. The full 5-crate
workspace (`loki-connectors-sdk`, `loki-ipc`, `loki-monitoring`,
`loki-runtime`, `loki-storage`) builds, formats, lints clean under
`-D warnings`, and all tests pass together (42 crate-internal unit tests plus
15 black-box integration tests for this crate alone; 100+ tests workspace-wide,
all green).

One material, documented deviation from the packet's literal migration
instruction: see §5 and §7 — the new telemetry tables live in this crate's
own self-contained SQLite database/migration, not
`crates/loki-storage/migrations/`, because wiring the latter is not actually
achievable within this node's writable scope (explained below). This is
flagged for orchestrator review, not silently resolved.

## 5. Contracts, migrations, and compatibility

- Contracts changed: none — this is a new crate with no existing consumers
  yet (`MON-002` and IPC wiring are future nodes per this crate's own module
  doc: "not an IPC surface", "not a monitoring-rule engine").
- Consumers affected: none yet.
- Migration: new — `crates/loki-monitoring/migrations/0001_telemetry.sql`,
  applied by this crate's own idempotent migration runner
  (`src/store.rs::migrations`) against this crate's own SQLite database file
  (opened via `SqliteTelemetryStore::open(path)`), **not** registered in
  `crates/loki-storage/src/migrations.rs`'s `MIGRATIONS` constant and **not**
  physically located in `crates/loki-storage/migrations/`.

  **Why this deviates from the packet's literal instruction** ("new migration
  file in `crates/loki-storage/migrations/` if a new table is needed"): I
  traced the actual mechanics before accepting the prior worker's approach.
  `crates/loki-storage/src/migrations.rs`'s `MIGRATIONS` constant is the only
  code that embeds/registers a migration file — adding a `.sql` file to
  `crates/loki-storage/migrations/` alone does nothing; it must also be
  registered by editing `crates/loki-storage/src/migrations.rs`, which is a
  source file, not the `migrations/` directory, and is explicitly outside
  this node's writable scope (`Docs/graph/tasks/MON-001.md` §2: "Do not
  touch ... `crates/loki-storage/**` directly"). Separately,
  `loki_storage::Storage`'s underlying connection is `pub(crate)`-only, so no
  external crate can execute reads/writes against it without `loki-storage`
  itself exposing a new public repository seam — again an edit to
  `loki-storage/src` this node cannot make. Given that, the literal packet
  instruction ("migration file there") and the packet's own forbidden-scope
  boundary are in direct tension: the instruction is not actually executable
  without also violating the boundary. I resolved this the way `AGENTS.md`'s
  source-of-truth order and task-hygiene rules direct — state the necessary
  assumption in the handoff rather than silently reaching into forbidden
  scope, and choose the smallest in-scope solution: this crate owns a second,
  independent SQLite database file with its own migration, own connection,
  own idempotent migration runner mirroring `loki-storage`'s pattern. This is
  functionally correct (proven by the restart tests) but is an architecture
  decision — "two separate SQLite databases" vs. "one shared database with a
  `loki-storage`-owned seam for other crates to write through" — that the
  orchestrator/an ADR should explicitly ratify or override, not something a
  single bounded node should decide permanently on its own. See §7 and §9.

## 7. Decisions and assumptions

- **Self-contained telemetry store instead of a `loki-storage`-hosted
  table.** See §5 for the full mechanical reasoning (the packet's migration
  instruction and its forbidden-scope boundary are mutually exclusive as
  literally written). I verified this by reading
  `crates/loki-storage/src/migrations.rs` and `crates/loki-storage/src/
  storage.rs` directly rather than trusting the prior worker's own doc
  comment at face value — the `pub(crate)` connection and the
  compile-time-embedded `MIGRATIONS` constant are both real, current
  constraints, not a misreading. This is the one point in this handoff most
  likely to warrant orchestrator pushback; see §9 for the proposed follow-up.
- **No fixed freshness-window default.** `FreshnessTracker::assess` takes an
  explicit `now`/`window` from the caller rather than this crate inventing a
  default staleness threshold, since `Docs/SPEC.md` does not define one and
  it is necessarily source/metric-specific. This matches the packet's stop
  condition's spirit (do not invent unspecified product behavior) even
  though the stop condition itself only names connector-specific *fields*,
  not thresholds.
- **Drop-oldest, not reject-new, for buffer overflow.** Documented in
  `src/buffer.rs`'s module doc: telemetry ingest is a live stream where
  recency is normally the priority signal for a monitoring consumer: this is
  a reasonable default, not something `Docs/SPEC.md` mandates explicitly —
  flagged here in case a reviewer disagrees with the tradeoff for a specific
  future consumer's needs (`MON-002` could still choose per-signal policy
  later; this crate's `BoundedBuffer` itself is generic and does not hardcode
  drop-oldest at the type level beyond `Pipeline`'s current wiring).
- **`quality` is caller-supplied, never inferred.** `SampleQuality` (`good`/
  `late`/`gap`/`invalid`, the closed `Docs/SPEC.md` §3.5 vocabulary) is set
  by whatever ingests into this pipeline, not guessed by this crate from a
  fabricated "late" cutoff — this crate only *mechanically* detects sequence
  gaps itself, which is a structural computation, not an invented business
  rule.
- **In-memory working state does not survive restart; durable data does.**
  Documented at length in `src/pipeline.rs`'s module doc and directly
  tested (`tests/restart.rs::in_memory_working_state_honestly_resets...`).
  This was a deliberate choice to avoid either fabricating pre-restart
  freshness or silently treating it as still valid, per `Docs/SPEC.md` §4.3.

No unresolved assumption here changes this node's own acceptance criteria —
all 7 deliverables pass as written. The storage-siting decision above is a
persistence-architecture question for a later/parallel node, not a gap in
this node's own scope.
