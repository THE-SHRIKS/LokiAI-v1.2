flagged architectural gap (Section 3, Section 12 stop condition 1) is real and
blocking: `loki-connectors-sdk` gives a connector no typed channel to report

scope for this node and triggers stop condition 1 in Section 12. No source

## 7. Decisions and assumptions — Section 9 open questions handled explicitly, not silently

Per the packet's Deliverable 8 and Section 9, both named open questions are
recorded here as **inherited-but-not-resolved by this node**, since this node
never reached the point of writing reconciliation code that would embody a
resolution:

1. **No minimum `IdentityConfidence` threshold policy exists (Section 9 item
   1).** This node makes no choice here — it never obtained a real
   `IdentityConfidence` value from anywhere, because nothing in
   `loki-connectors-sdk`'s `Connector`/`StageOutcome`/`StageEvidence` surface
   lets a connector report one. There is no "stopgap behavior" to describe;
   the gap is upstream of where a threshold decision would even apply. This
   is not a decision to leave unmade — it is a precondition (Deliverable 1/2:
   "accepts `TransportCandidate`... interpret the result into a real
   `IdentityProbeResult`") that cannot be reached at all without an SDK
   change. The policy gap remains fully open for whatever future node adds
   the typed evidence channel; it must decide the threshold at the same time
   it decides how evidence is reported.

2. **`loki_connectors_sdk::identity` validates wire-data shape only, not
   independent HMAC authenticity (Section 9 item 2).** This node confirms, as
   an architectural fact verified by reading `crates/loki-connectors-sdk/src/
   connector.rs`, `operation.rs`, and `tests/support/mod.rs` (this crate's own
   `TestConnector`, which mirrors the only realistic in-process connector
   shape available at this milestone): connectors registered with
   `loki-connector-registry` are in-process `Box<dyn Connector>` trait
   objects with no `loki-ipc`/wire dependency anywhere in this crate's
   dependency graph. Had this node been able to proceed, it would never have
   called `IdentityProbeResult::from_json_str` on untrusted wire/JSON data —
   there is no wire boundary inside this registry crate for it to parse
   across. This is stated as a fact about this crate's actual architecture
   (verified by inspection, not assumed), not a decision this node is making
   on the wire-authenticity question itself, which remains open for whatever
   future component (if any) does cross a real wire boundary for connector
   identity data (e.g. an out-of-process/third-party connector host per
   `Docs/CONNECTOR_SPEC.md` §12, which does not exist yet).

Additional decisions/assumptions:

- Did not attempt a partial implementation that satisfies only the
  busy/permission/disconnect deliverable (achievable today via
  `ConnectorError.code`, since that field is documented as an open,
  caller-classifiable identifier, unlike `StageEvidence.summary`) while
  leaving identity reconciliation unbuilt. A partial pass would produce a
  registry with half a contract (classified failures, but candidates that
  succeed `identify` still cannot produce a real `PublicDeviceIdentity`),
  which is a worse state to hand off than a clear, evidence-backed
  `NEEDS_REPLAN`: it would invite whoever integrates this branch next to
  treat the mock-era `DeviceId`-from-candidate-string minting as still
  "mostly fine" for the success path, exactly the anti-pattern this packet
  exists to remove.
- Did not invent a workaround encoding structured identity data into
  `StageEvidence.summary` (e.g., JSON-in-a-string) or `evidence_ref`
  (opaque string). Both are explicitly documented in `loki-connectors-sdk` as
  free-text/opaque-reference fields, not typed identity-evidence carriers;
  treating them otherwise would be exactly the "undocumented free-text
  convention" Section 3 says not to invent, and would let two unrelated
  connectors that happen to return the same success-message text collide to
  the same fabricated fingerprint digest — a concrete instance of the
  "incorrect merge of two distinct physical devices into one identity"
  failure mode the packet's own Section 10 warns about.
