## 7. Decisions and assumptions

1. **`IdentityConfidence` handling (Section 9 open question 1 — not silently
   resolved).** This node accepts any confidence level a connector reports,
   `Weak` included, as sufficient to produce a `PublicDeviceIdentity`, via
   `IdentityProbeResult::verified` (which itself places no confidence floor
   on its input). This is an explicit stopgap documented in `discovery.rs`'s
   module doc, not a considered security policy: no minimum-confidence
   threshold has been decided anywhere in this codebase, and this node does
   not invent one. A future decision node must set that policy (coupled to
   whatever evidence-reporting shape is in use, per
   `CON-SDK-IDENTITY-EVIDENCE-001`'s own handoff §9) before any consequential
   capability is gated on identity confidence.
2. **Untrusted wire-data boundary (Section 9 open question 2 — not silently
   resolved).** This node never calls `IdentityProbeResult::from_json_str`
   and never constructs an `IdentityProbeResult` from anything other than a
   real, in-process `LifecycleOutcome` obtained by calling `run_operation`
   against an already-registered `Box<dyn Connector>` trait object.
   Registered connectors are in-process trait objects with no `loki-ipc`/wire
   dependency anywhere in this crate's dependency graph (confirmed by
   inspection of this crate's own `Cargo.toml`, §3 above — no `loki-ipc`
   dependency exists), so there is no untrusted-wire boundary for this
   module to cross at this milestone. This is stated as an architectural
   fact about this crate's current shape, not a resolution of the
   wire-authenticity question itself, which remains open for whatever future
   component (e.g. an out-of-process connector host, `Docs/CONNECTOR_SPEC.md`
   §12) actually crosses a real wire boundary for connector identity data.
3. **Busy/permission/disconnected/unsupported classification convention
   (Deliverable 4).** `Docs/CONNECTOR_SPEC.md` §5 requires `identify` to be
   able to return "a structured unsupported/permission/busy/error result" but
   does not standardize the error-code vocabulary. This node defines its own
   registry-owned convention in `discovery.rs`'s `DiscoveryFailureClass::classify`:
   `"transport_busy"`/`"device_busy"`/`"port_busy"` → `Busy`;
   `"permission_denied"`/`"access_denied"` → `PermissionDenied`;
   `"device_disconnected"`/`"device_not_found"`/`"candidate_absent"` →
   `Disconnected`; `"unsupported_candidate"`/`"unsupported_device_family"`/
   `"unsupported"` → `Unsupported`; anything else → `Generic`. A connector
   author who wants a specific class recognized reports one of these exact
   `code` strings. This is this crate's own policy (not a
   `loki-connectors-sdk` contract change) and is documented in code, not
   invented silently.
4. **Cross-candidate reconciliation delegates its fail-closed guarantee to
   `IdentityProbeResult::verified` itself**, rather than this crate
   re-implementing digest comparison: `registry.rs::reconcile_connector_probes`
   gathers every piece of evidence a connector's candidates produced this
   cycle and calls `verified(...)`; if it errors (digest mismatch), that is
   treated as `reconciliation_conflict: true` and no identity is accepted for
   any of that connector's candidates this cycle, and the persisted
   reconciliation state for that connector is left untouched. This means the
   SDK's own security-relevant fail-closed check is the single source of
   truth for what counts as a conflict, not a second, potentially-divergent
   implementation in this crate.
5. **`ObservedCandidate` carries `candidate_id` alongside `TransportCandidate`**
   rather than this crate reading it back out of `TransportCandidate`'s
   private field via its `Serialize` impl. `TransportCandidate` (read-only
   dependency) has no public getter for `candidate_id`; the caller that
   constructs a `TransportCandidate` via `TransportCandidate::new(candidate_id,
   ...)` already has that string, so `CandidateSource::candidates_for` asks
   for it once more, paired with the candidate. This avoided adding a
   `serde_json` dependency (which would have required an out-of-scope
   `Cargo.toml` edit) and avoided a fragile reflection-style workaround.
6. **`CandidateSource: Sync`** — added as a supertrait bound (not present in
   the first draft) after `cargo build` showed `run_discovery_cycle`'s
   `&dyn CandidateSource` parameter, held across `.await` points, must be
   `Send`/`Sync` for this crate's own concurrency test to spawn discovery
   cycles onto separate tokio tasks. Every closure this crate or its tests
   use as a `CandidateSource` only captures `Sync` data (string literals,
   other closures), so this costs real callers nothing; documented in
   `discovery.rs`.
7. **`identify` succeeding without attached identity evidence produces an
   honest `Unknown`** `IdentityProbeResult` (`discovery.rs::interpret_identify_outcome`),
   not a fabricated `Verified` result and not treated as a failure — a
   connector that implements `Connector` but not yet the identity-evidence
   attachment (e.g. an older or minimal connector) is not penalized with a
   spurious failure classification, but also never gets a `PublicDeviceIdentity`
   it did not earn.
8. **`AS-004` "no flash/restart capability offered" is verified only at the
   level this crate can control**: capabilities are static, declared once at
   registration from a connector's manifest (`crate::projection`, unchanged
   by this node); an unsupported `identify` result cannot dynamically grant
   or revoke a capability in this crate's current design, so the test
   (`unsupported_candidate_reports_unsupported_and_grants_no_capability`)
   proves the test double's manifest (which only ever declared `identify`)
   stays exactly that after an unsupported result — a stronger dynamic
   capability-gating story is out of this node's scope and not implied by
   the packet's deliverables.

## 8. Review focus

- Confirm `reconcile_connector_probes`'s reliance on `IdentityProbeResult::verified`'s
  own digest-consistency check (decision 4, §7) is the right trust boundary:
  this crate never independently re-derives or compares raw digest strings
  itself except by delegating to the SDK's own validated constructor.
- Confirm the `IdentityConfidence`-acceptance stopgap (decision 1) is
  correctly understood as *not* a security decision this node made — it is
  the absence of one, explicitly flagged for a future policy node, matching
  the packet's own Section 9 instruction not to invent a threshold.
- Confirm `ObservedCandidate` (decision 5) does not itself become a new
  place a caller could smuggle a mismatched `candidate_id`/`TransportCandidate`
  pair — this node treats `CandidateSource` as a fully in-process, trusted
  boundary (same trust level as this crate's existing `ctx_factory` closure
  parameter), consistent with decision 2's "no untrusted wire boundary"
  finding; a future out-of-process candidate source would need its own
  validation layer, out of this node's scope.
- Confirm `mark_absent_connectors`'s absence sweep (registry.rs) is scoped
  correctly: only connectors that reported *zero* candidates this cycle are
  swept to `live: false`; a connector whose candidates were present but
  whose `identify` calls failed (busy/permission/generic) is deliberately
  left alone (decision documented in `registry.rs`'s module doc,
  "A connector whose candidates were present but whose `identify` calls
  simply failed... is not swept into `newly_absent`").
